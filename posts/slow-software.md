title: Slow Software
date: 2026-09-30
description: In defense of tools that do less, quickly, and then leave.
---

There is a kind of software that asks nothing of you. It opens, it does the one thing it was made for, and it gets out of the way. I have been trying to make more of it.

## The cost of motion

Every spinner is a small apology for a decision made somewhere else. Every skeleton screen is a promise that something is coming, which is another way of saying that nothing is here yet.

Speed is a feature. So is calm, and we rarely budget for both.

> A good tool should feel like a hand, not a host.

The distinction matters more than it sounds. A hand waits to be used. A host has opinions about how long you should stay, what you should look at next, and whether you would like to hear about the newsletter.

## What to keep

When I am deciding whether a feature belongs, I ask three questions:

1. Does it still work when the network is slow?
2. Can someone understand it without a tour?
3. Would I miss it if it disappeared tomorrow?

Most things fail the third question, and most things should. The features that survive it tend to be small, obvious, and a little bit boring—which is another way of saying they are load-bearing.

## A practice

I have started opening new projects in a plain text editor and leaving them there for a week. No framework, no hot reload, no component library. If the idea survives seven days of `<p>` tags, it is probably worth building properly.

If it doesn't survive, nobody was hurt. There is no repository to archive, no dependency to update, no migration to write. The idea simply returns to the air, where it came from.

This is not a argument against tools. It is an argument for waiting until the tool is the smallest part of the work.
